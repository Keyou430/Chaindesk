# ChainDesk M3 implementation and acceptance

M3 passed 141 checks in disposable guest `m3-v1QbIK` under a standard user. The maintainer selected internal development acceptance only on 2026-11-18; this milestone is not a public release.

## Scope and reuse

The approved execution plan sections 7–10 and 14.4 define the reliability scope. Local tracking is `.chaindesk/remaining-work/M2-M5-local-issue.md`. The M0, M1 and M2 seals remain immutable.

| Import path | Signature or boundary | Responsibility and reuse |
| --- | --- | --- |
| `crate::core::chain_diagnostic` | `Diagnostic::start(config: Mapping) -> Result<Self>` | Validate and probe a job-owned isolated core; reuse fixed core/resource leases, private controller directories and port-conflict handling. |
| `crate::core::chain_probe` | `probe(port: u16) -> Result<Option<ProbeObservation>>`, `verify(observation, expected)` | Reuse explicit loopback proxy clients and verified HTTPS; retain both IPv4 source observations. |
| `crate::feat::chain` | `connect(input: ConnectInput) -> Result<ChainView>`, `restore_last_good()` | Serialize candidate selection, isolated and working checks, commit and rollback through the existing operation mutex and protected store. |
| `crate::core::CoreManager` | Working-core startup and termination | Reuse process jobs and validated configuration; require bounded authenticated application before publishing readiness and reconcile unexpected termination independently of background checks. |
| `crate::core::portable_proxy` | Owned proxy session and durable journal | Extend exact proxy snapshots with current-user DPAPI, restricted files and explicit conflict handling. |
| `crate::core::process_identity` | `Process::verify(expected: &Identity) -> Result<Self>` | Bind process access to PID, creation time, executable and user; reuse the verified identity for cleanup and watchdog ownership. |
| `crate::core::proxy_watchdog` | `ensure() -> Result<Arc<Watchdog>>`, `Watchdog::verify_alive()` | Run an authenticated recovery process from the same executable; provide a recovery entry before WebView startup. |
| `crate::core::portable_network` | `start() -> Result<Self>`, `take_changed()` | Observe native network changes without replacing ordinary health-check ownership. |
| `crate::feat::chain_diagnostics` | `preview()`, `export(path: String, expected_sha256: String)` | Produce a bounded allowlisted JSON snapshot; export only the exact reviewed hash to a new private file. |
| `@/pages/chain` / `@/services/cmds` | Typed chain commands and committed selected-front state | Reuse ordered mutations, query caching and existing page controls; display the verified front and separate pending selection. |

No package versions or new third-party dependencies were introduced. Tauri runtime tracing was disabled after review identified an unsafe cross-thread reference-counting path; business tracing remains enabled. The earlier native startup abort is consistent with that hazard but was not conclusively attributed by a stack trace.

## Defined behavior

| Boundary | Implemented definition |
| --- | --- |
| Connection transaction | A 30-second total budget covers operation acquisition, at most three eligible automatic candidates, isolated validation and working-chain checks. Cancellation removes candidate jobs and retains a valid prior session. |
| Readiness | Listener/process validation and authenticated synchronous working-configuration application share a bounded readiness operation before Started is published. |
| IPv4 baseline | Both source results remain visible. Only an explicitly confirmed current agreeing observation becomes a comparison baseline; mismatch, disagreement or unavailability cannot silently overwrite it. |
| Switching | Commit the new front only after isolated and working checks; restore and recheck the last working chain if application fails. The fixed exit is retained. |
| Background checks | Opt-in HTTPS health every 60 seconds and IPv4 every 300 seconds. Three failures mark degradation; recovery and automatic front replacement require fresh checks, proxy permission and a live verified watchdog. |
| Core exit | An observed owned-core termination invalidates Connected even when background requests are disabled, clears stopped private configuration and requires an explicit verified reconnect. |
| Proxy recovery | Preserve exact value presence, type and bytes for the four owned WinINET values. The journal and watchdog bind ownership to the process, user and session; foreign changes produce a visible conflict. |
| Crash recovery | Parent termination closes the owned core job. Watchdog recovery, next-startup recovery and independent `recover-proxy.cmd` use the durable journal; independent recovery does not require an available WebView2 runtime. |
| Diagnostics | Preview contains bounded health observations and error codes, excluding credentials, subscription tokens and node identities. Export checks the reviewed SHA-256 and refuses overwrite or a changed snapshot. |

## Review corrections and failed-run boundaries

The final review found seven important issues. The author corrected runtime tracing, the working-core readiness barrier, recovery ownership gates for monitoring, opted-out core-exit reconciliation, committed-front UI state, stopped-session-only plaintext assertions and strict runner shutdown acceptance. Fresh guest assertions exercise the lifecycle, ownership and UI corrections; resolved runtime features and real shutdown-gate logic were checked separately.

Failed runs remain excluded from milestone acceptance. Two later failures were harness problems: the runtime-removal fixture raced natural WebView2 exit, and a preservation assertion compared bytes across an intentional original-client configuration write. The accepted harness retains exact process handles while waiting for owned browser exit and establishes a new baseline only after an explicit external-client mutation. Product recovery must preserve that new file fingerprint and every foreign proxy value; these assertions were not waived.

Public M4 delivery still requires approved publisher signing, missing plugin license grants and redistribution materials, and the final signed standard/full package environment matrix. M5 requires real participant/payment observations over at least 14 calendar days. At the maintainer's 2026-11-18 instruction, public distribution, publisher signing and paid trials are deferred; the current delivery is the accepted internal development full package and its evidence. TUN, Windows 10, ARM64 and non-Windows support remain outside accepted first-release scope.
